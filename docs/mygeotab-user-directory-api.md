# MyGeotab User Directory API Notes

## Findings

- The MyGeotab `Get` method accepts an entity `typeName` such as `User`. With no search criteria, it returns all entities available to the authenticated API session in the database being queried. The result is not a global directory across databases. [Get method](https://developers.geotab.com/myGeotab/apiReference/methods/Get/)
- The `User` object exposes `name` as the user's email/login name, `firstName`, `lastName`, `activeFrom`, and `activeTo`. The activity dates indicate the period for which the user is active. [User object](https://developers.geotab.com/myGeotab/apiReference/objects/User/)
- The documented `User` properties include `securityGroups`, `userRole` (primary functional role, default `null`), `customUserRole` (user-entered label when the role is `Other`), and `isDriver`. `securityGroups` contains Group references that define user access; resolve their IDs against `Get` with `typeName: "Group"` and `search: { id: "GroupSecurityId" }` to display the security-clearance group names as clearance labels. [User object](https://developers.geotab.com/myGeotab/apiReference/objects/User/) · [Group object](https://developers.geotab.com/myGeotab/apiReference/objects/Group/) · [SecurityFilter object](https://developers.geotab.com/myGeotab/apiReference/objects/SecurityFilter/)
- The User object documents `userAuthenticationType`. It distinguishes BasicAuthentication and MyAdmin accounts, and notes that MyAdmin users are not visible to BasicAuthentication users. Therefore, a `Get User` result is not necessarily every account that could authenticate to the database through another account type. [User object](https://developers.geotab.com/myGeotab/apiReference/objects/User/)

## Implications for this add-in

- A Users page can query `Get` with `typeName: "User"` and display the user records visible to the current MyGeotab session. The caller's database access and permissions still apply.
- Treat the result as a directory of visible database user records, not proof that each person can successfully sign in at this moment. Authentication credentials, external identity configuration, and database access are separate concerns; do not request or display password data.
- The **Drivers & Users** page is restricted to users with **`Administrator`** security clearance (hidden from navigation for non-Administrators with fail-closed guards). It provides two sub-tabs: **Drivers** (operational availability board showing `Active drivers`, `Available now`, `On trip now`, and current/next approved trips) and **All users** (account directory showing **Name**, **Email / login**, **Clearance**, **Driver status**, and **Account status**, omitting the unused Functional role column). Resolve clearance labels from each user's `securityGroups` references and matching Group names. Normalize the known built-in technical names `EverythingSecurity`, `SupervisorSecurity`, `DefaultSecurity`, `DriveUserSecurity`, `ViewOnlySecurity`, and `NothingSecurity` to the MyGeotab UI labels `Administrator`, `Supervisor`, `Default user`, `Drive App user`, `View only`, and `Nothing`; preserve API names for custom clearances. If group lookup fails, show `Not available`; if a user's group ID is absent from the successful lookup, show `Unmapped clearance`.
- **Approval & Directory authorization (`Administrator` clearance):** By product policy, only users whose resolved MyGeotab security clearance is **`Administrator`** (built-in `GroupEverythingSecurityId` / `EverythingSecurity`) are authorized to view the **Approval** and **Drivers & Users** navigation tabs and perform **Approve**, **Reject**, or admin **Cancel** actions. Functional role (`userRole`) and driver status (`isDriver`) do not grant approval authority.
- **Fail-closed clearance check:** When initializing the add-in, check the signed-in user's clearance using `Get User` (filtered by the session `userName`) and `Get Group` (`GroupSecurityId`). If either lookup fails or is denied for a restricted account, fail closed (`isAdministrator = false`): hide the **Approval** tab and block approval actions without preventing the user from creating or viewing their own bookings.
- **Security boundary:** Because this add-in runs client-side in the browser and non-admin requesters require `AddInData` write access to submit bookings, restricting Approval to `Administrator` clearance is UI/application-level enforcement backed by audit fields (`reviewedBy`, `reviewedAtUtc`) rather than server-side enforcement on `AddInData`. Hard server-side RBAC requires a backend service.
- **Driver assignment eligibility:** When an Administrator approves a booking, the **Driver** selector must only allow active driver accounts—users with `isDriver === true` whose derived account status (`activeFrom` / `activeTo`) is `Active`. Inactive or scheduled driver accounts must be excluded from new assignments.
- If the product requires a complete list across BasicAuthentication and MyAdmin account types, validate the required access and expected visibility in the target database before promising that the add-in can show every account.
